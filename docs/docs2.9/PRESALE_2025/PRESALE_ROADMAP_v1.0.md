### QR Wallet System

**Architecture:**
```
User purchases → Payment confirmed → Generate QR code

QR Code contains:
├─ Unique Wallet ID (UUID)
├─ Token amount
├─ Redemption code (encrypted)
├─ Expiry date (1 year after mainnet)
└─ Signature (prevents tampering)

Database record:
├─ Order ID
├─ User email (KYC verified)
├─ ZION amount
├─ EUR paid
├─ Payment method
├─ Timestamp
├─ Redemption status (pending/claimed)
└─ Destination address (after claim)
```

**Redemption Process:**
1. User receives QR code via email
2. Downloads ZION wallet (mainnet live)
3. Scans QR code in wallet
4. Wallet generates new address (or uses existing)
5. Backend verifies QR signature
6. Tokens transferred from escrow to user address
7. QR marked as redeemed (one-time use)

**Security:**
- QR codes encrypted with AES-256
- Rate limiting on redemption API
- Email verification before claim
- Multi-sig escrow (3-of-5 keys: team members + external custodian)
- Time-locked smart contract (prevents premature claims)

### Smart Contract (Presale Escrow)

```solidity
// Simplified example (actual implementation more complex)

pragma solidity ^0.8.0;

contract ZIONPresaleEscrow {
    address public multiSigWallet;
    mapping(bytes32 => uint256) public qrAllocations;  // QR hash → amount
    mapping(bytes32 => bool) public claimed;
    
    uint256 public constant TOTAL_PRESALE = 500_000_000 * 1e6;  // 500M ZION
    uint256 public totalClaimed;
    
    event QRRedeemed(bytes32 indexed qrHash, address indexed recipient, uint256 amount);
    
    function redeemQR(
        bytes32 qrHash,
        bytes memory signature,
        address recipient
    ) external {
        require(!claimed[qrHash], "Already claimed");
        require(verifySignature(qrHash, signature), "Invalid signature");
        
        uint256 amount = qrAllocations[qrHash];
        require(amount > 0, "Invalid QR");
        
        claimed[qrHash] = true;
        totalClaimed += amount;
        
        // Transfer ZION tokens to recipient
        _transferZION(recipient, amount);
        
        emit QRRedeemed(qrHash, recipient, amount);
    }
    
    // Additional functions: emergency withdrawal, refunds, etc.
}
```

## ⚠️ RISK FACTORS & MITIGATION

### Regulatory Risks
**Risk:** MiCA or local regulations change, token sale becomes non-compliant  
**Mitigation:**
- Regular legal reviews (quarterly)
- Flexible T&C allowing refunds if regulatory issues
- Geographic restrictions (exclude high-risk jurisdictions)
- Escrow structure allows freezing/returning funds

### Market Risks
**Risk:** Crypto bear market, low demand for presale  
**Mitigation:**
- Conservative funding targets (€2.5M minimum viable)
- Dynamic pricing (can adjust phases if needed)
- Long presale window (3+ months)
- Strong utility value proposition (not speculation-driven)

### Technical Risks
**Risk:** Smart contract bugs, QR system hacked  
**Mitigation:**
- Multiple security audits (CertiK + OpenZeppelin)
- Bug bounty program (pre-launch)
- Multi-sig wallets (no single point of failure)
- Insurance coverage (if available)
- Gradual rollout (soft launch first)

### Operational Risks
**Risk:** Team capacity, development delays  
**Mitigation:**
- Realistic timelines (12-18 months mainnet)
- Transparent roadmap updates
- Buffer capital (10% contingency)
- Experienced advisors & contractors

### Legal/Tax Risks
**Risk:** Unexpected tax liabilities, legal disputes  
**Mitigation:**
- Professional accounting firm (crypto-specialized)
- Tax provisions (35% of revenue reserved)
- Legal insurance (directors & officers)
- Clear T&C with arbitration clauses
