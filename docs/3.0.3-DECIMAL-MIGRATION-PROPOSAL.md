# ZION 3.0.3 — Proposal: 12 → 6 Decimal Migration with State Preservation

> **Status:** DRAFT proposal (not approved, not implemented).
> Author: Copilot, 2026-06-25, requested by repo owner.
> Scope: design only — no L1 code changes in this document.
> **Reading order:** §1 motivation → §2 options → §3 recommended path
> → §4 step-by-step runbook → §5 risks → §6 open questions.

## 1. Motivation

Current state: `FLOWERS_PER_ZION = 1_000_000_000_000` (10¹²) in
[`V3/L1/core/src/emission.rs`](../V3/L1/core/src/emission.rs).

Pain points:

1. Numbers are unergonomic for humans: block reward = 5 400 067 000 000 000.
2. Bridge math is asymmetric: L1 (12) → EVM (18) is ×10⁶, but L1
   (12) → Cardano/Cosmos (6) is ÷10⁶ — every cross-chain path needs
   custom logic, no clean 1:1 anywhere.
3. RPC wire format already drifted: `_flowers`, `_atomic`,
   mis-named `_zion` all coexist (see
   [`CANONICAL_UNITS_AUDIT.md`](./CANONICAL_UNITS_AUDIT.md) §3b).
4. Sub-micro-ZION precision (10⁻⁷..10⁻¹² ZION) has no real-world
   use case at our fee level (typical fee = 5 × 10⁹ flowers = 0.005 ZION;
   even with 6 decimals we keep 0.001 ZION = 1 000 micro-ZION granularity).

Proposed change: `FLOWERS_PER_ZION = 1_000_000` (10⁶).

Result table:

| Metric | Current (10¹²) | Proposed (10⁶) | Win |
|--------|----------------|----------------|-----|
| 1 ZION | `1 000 000 000 000` fl | `1 000 000` fl | shorter |
| Block reward | `5 400 067 000 000 000` fl | `5 400 067 000` fl | fits u32 |
| Total supply | `1.44 × 10²³` fl | `1.44 × 10¹⁷` fl | u64 still safe |
| Min fee | `5 × 10⁹` fl (= 0.005 ZION) | `5 × 10³` fl (= 0.005 ZION) | identical real value |
| Bridge → wZION (EVM 18) | ×10⁶ | ×10¹² | XMR/Monero style |
| Bridge → Cardano (6) | ÷10⁶ | **×1 (1:1)** | huge simplification |
| Bridge → Cosmos (6) | ÷10⁶ | **×1 (1:1)** | huge simplification |
| Bridge → Solana (9) | ÷10³ | ×10³ | symmetric |

## 2. Migration Options (with state preservation goal)

### Option A — Full re-genesis (status quo of GENESIS_REGENERATION_RUNBOOK)

- New genesis at height 0 with hard-coded premine.
- **Loses:** all mined supply since launch (currently ~82 M ZION
  across blocks 1..15 259), all miner payout history, all
  on-chain DAO state.
- **Keeps:** nothing dynamic — only the 14 premine outputs, recomputed
  with new units.
- Effort: ≈ runbook we already have. Lowest engineering risk.
- **Acceptable?** No — user explicitly wants to avoid "starting from 0".

### Option B — State snapshot → re-genesis with snapshot baked in ⭐ RECOMMENDED

- Pick a target block H (last block on the old chain).
- Snapshot at height H: full UTXO set + account balances + DAO state +
  bridge locks.
- For every amount in the snapshot:
  `new_amount = old_amount / 10⁶` (integer division), recording the
  rounding loss as a system-attributed "dust burn" (or as additional
  miner fee for the H+1 block).
- Build a **new genesis block at height 0** whose coinbase outputs
  encode the snapshot:
  - 14 original premine outputs **converted** to new units (same
    public addresses, divided amounts).
  - 1..N "post-mining snapshot" outputs, one per UTXO + one per
    account-model balance from the snapshot.
- Start a new chain with the same chain-id but a new genesis hash.
- **Keeps:** every satoshi-equivalent of value (modulo dust under
  10⁶ flowers ≈ 10⁻⁶ ZION ≈ 1 micro-ZION).
- **Loses:** block 1..H header history, hashes, mining record,
  individual tx history (only aggregated balances survive).
- Effort: ≈ runbook + a new snapshot exporter binary
  (`zion-cli snapshot --at-height H --out snapshot.json`) + a new
  genesis builder that takes `snapshot.json` as input.
- Re-uses the existing `GENESIS_REGENERATION_RUNBOOK.md` for the
  cryptographic & operator steps.

### Option C — In-place hard fork with denomination switch at activation height

- Define `DENOMINATION_SWITCH_HEIGHT = X`.
- Blocks 0..X-1 keep the old emission constant (`FLOWERS_PER_ZION_LEGACY`).
- Block X and onwards switch to `FLOWERS_PER_ZION_NEW`.
- Every state read crossing the boundary needs runtime conversion:
  pre-X UTXOs carry a flag "legacy units", a one-time validator
  applies `÷10⁶` when those UTXOs are spent into a post-X block.
- **Keeps:** entire chain history, hashes, tx record.
- **Loses:** nothing on-chain, but adds permanent code complexity
  forever (every consensus path now has a "before/after switch"
  branch).
- Effort: large. Requires deep changes in `validation.rs`,
  `consensus.rs`, `wallet.rs`, RPC formatters, and every client
  (desktop, mobile, pool, bridge).
- Real precedent: Belarusian rouble denomination, but no major
  blockchain has done it cleanly.
- **Verdict:** technically possible, operationally a maintenance
  nightmare. Not recommended.

### Option D — Display-only change (no consensus impact)

- Keep `FLOWERS_PER_ZION = 10¹²` everywhere internally.
- Introduce a display unit `microzion = 10⁶ flowers` and rewrite
  every wallet/explorer/website UI to render `μZ` instead of `ZION`.
- **Keeps:** everything, no fork.
- **Loses:** nothing on chain.
- **But:** doesn't actually solve the bridge math problem — every
  cross-chain conversion still needs ×10⁶ / ÷10⁶ adjustments
  internally. Only the user-visible numbers change.
- **Verdict:** cosmetic, kicks the can down the road. Useful as a
  short-term workaround if we decide to delay the real migration.

## 3. Recommended Path: Option B (Snapshot + Re-Genesis)

### 3.1 Why now is the right time

Three independent pressures already point to re-genesis BEFORE the
mainnet public launch:

1. We just discovered the `getBlockTemplate._zion` field is mis-named
   and contains flowers — fixing it cleanly requires bumping the RPC
   contract anyway (see [`CANONICAL_UNITS_AUDIT.md`](./CANONICAL_UNITS_AUDIT.md) §3b.3).
2. The DAO daemon and explorer ecosystem are still pre-launch — no
   real-money tx history depends on the current block hashes.
3. The migration would lock in the canonical RPC naming
   (`_flowers` everywhere) in the same release as the unit change,
   so the next mainnet contract is stable for years.

Doing the decimal migration as part of the planned pre-launch
re-genesis is **cheap**. Doing it later as a hard fork is **expensive**.

### 3.2 What survives Option B

Layer | Survives | Notes
------|----------|------
14 premine wallets (humanitarian, ISSOBELLA, OASIS slots, DAO treasury, etc.) | ✅ amount converted | Same addresses, amounts ÷10⁶ rounded
Mined-since-launch supply (~82 M ZION) | ✅ amount converted | Aggregated per address into a snapshot output
Pool payout history (PPLNS) | ⚠️ aggregated balance only | Per-share record is lost; current pending balances are preserved
DAO proposals / votes | ⚠️ closed proposals lost | Active proposals must be re-submitted
DAO treasury balance | ✅ amount converted | Single output to treasury address
Bridge locks | ⚠️ manual reconciliation | wZION on EVM keeps 10¹⁸ wei representation; bridge operator re-mints with new conversion factor (×10¹²)
Atomic-swap HTLCs | ⚠️ must complete before snapshot height H | Open HTLCs at H need refund or pre-snapshot settlement
Block 1..H headers & tx hashes | ❌ lost | Explorer "old chain" view becomes archival-only

## 4. Step-by-Step Runbook (Option B, draft)

This is a **draft** — every step must be reviewed and signed off by
the repo owner before any execution. Mirrors the structure of
`docs/GENESIS_REGENERATION_RUNBOOK.md`.

### Phase 0 — Pre-flight (T-7 days)

- [ ] Freeze pool deposits / withdrawals.
- [ ] Notify any external integrators (none today, easy).
- [ ] Tag current code: `git tag pre-decimal-migration` for rollback
      reference.
- [ ] Snapshot Edge VM (Hetzner cloud snapshot).

### Phase 1 — Snapshot export (T-2 days)

- [ ] Implement `zion-cli snapshot export --at-height H
      --out snapshot.json --include-utxo --include-accounts
      --include-dao --include-bridge`.
- [ ] Run on Edge node:
      `zion-cli snapshot export --at-height $(zion-cli height) ...`.
- [ ] Verify totals: sum of all snapshot amounts must equal
      `getSupplyInfo.circulating_supply_atomic` at H.
- [ ] Compute SHA256 of `snapshot.json` and pin it in a public commit.

### Phase 2 — Genesis rebuild (T-1 day)

- [ ] Implement `zion-cli genesis build --from-snapshot snapshot.json
      --new-decimals 6 --out new_genesis.rs`.
- [ ] Conversion rule:
      `new_amount = old_amount / 1_000_000` (integer division).
      Sum of rounding losses = "dust burn", documented but not
      credited anywhere.
- [ ] New genesis output layout:
      - Slots 0..13 → original 14 premine wallets, amounts converted.
      - Slot 14 → single output to a one-time "snapshot-receiver"
        address that holds aggregated mined supply, then a follow-up
        tx at H+1 distributes per the snapshot account list. (This
        keeps genesis.rs small; the distribution tx is the first
        real block.)
- [ ] Update `FLOWERS_PER_ZION` in `emission.rs` to `1_000_000`.
- [ ] Update all `block_reward` / fee constants by `÷10⁶`.
- [ ] Update bridge `FLOWERS_TO_WEI_FACTOR` from `1_000_000` to
      `1_000_000_000_000` (now ×10¹² because L1 has 6 decimals and
      EVM has 18).
- [ ] Update DAO daemon, atomic-swap daemon, WARP daemon — all
      `_atomic`/`_flowers` field handlers must be reviewed.

### Phase 3 — Test cycle (T-1 day)

- [ ] `cargo test -p zion-core --release` must pass with new constant.
- [ ] `cargo test --workspace -- --test-threads=1` must pass.
- [ ] Replay the snapshot on a local devnet: start node with new
      genesis, verify `getBalance` for every premine address returns
      `old_balance / 10⁶`.
- [ ] Replay the H+1 distribution tx, verify every account from the
      snapshot can spend.
- [ ] Bridge wrap/unwrap dry-run on a local Anvil EVM fork.
- [ ] RPC contract: every method audited per
      [`CANONICAL_UNITS_AUDIT.md`](./CANONICAL_UNITS_AUDIT.md) §3b.5
      — `_flowers` + `_zion_display` only, no more `_atomic`, no more
      mis-named `_zion`.

### Phase 4 — Cutover (T-0)

- [ ] Stop all Edge services: node1, node2, pool, bridge, DAO, swap,
      WARP, miner.
- [ ] Backup current DB (we keep it forever as `/data/legacy-mainnet/`).
- [ ] Deploy new binaries with new `emission.rs`.
- [ ] Start node with new genesis.
- [ ] Submit the H+1 distribution tx from a privileged operator
      wallet (genesis-issued signing key).
- [ ] Bring up pool, miner, bridge, DAO, swap, WARP.
- [ ] Smoke-test: `getBalance` for 3 random premine addresses →
      compare with `old_balance / 10⁶`.
- [ ] Update website, desktop agent, mobile app to point at new
      genesis hash.

### Phase 5 — Post-launch (T+1 day)

- [ ] Publish a public migration receipt:
      `docs/3.0.3-migration-receipt.md` listing:
      - Old genesis hash + new genesis hash
      - Snapshot height H
      - Snapshot SHA256
      - Total dust burned (rounding loss)
      - Address-by-address before/after table for the 14 premine
        wallets
- [ ] Tag `git tag v3.0.3-mainnet`.
- [ ] Keep legacy node binaries + DB available for archival explorer.

## 5. Risks

| Risk | Severity | Mitigation |
|------|----------|------------|
| Rounding loss > 0.000001 ZION × N accounts is "real money" lost | Medium | Document exact amount in migration receipt; offer compensation from a small set-aside DAO grant if total > 1 ZION |
| Snapshot exporter has a bug → balances diverge | High | Cross-verify with `getSupplyInfo` total and with a recompute from blocks 0..H |
| Bridge operator forgets to update conversion factor | High | Add a runtime assertion: `assert!(FLOWERS_PER_ZION == 1_000_000)` in bridge startup |
| Operators forget there are TWO different `FLOWERS_PER_ZION` constants depending on chain version | High | Rename in code to `FLOWERS_PER_ZION_V303` (with version suffix); old binaries crash loudly if loaded against new genesis |
| Active HTLC swap at snapshot height | Low | Block atomic-swap creation 24h before snapshot; refund any open HTLC at H-1 |
| External party already wrapped ZION → wZION before migration | Low (no public bridge yet) | If any wZION exists pre-migration, mint additional wZION × 10⁶ to those holders so the wei amount stays the same |

## 7. Comparison Cheat-Sheet

| Aspect | A (full re-genesis) | **B (snapshot + re-genesis)** ⭐ | C (in-place fork) | D (display only) |
|--------|---------------------|--------------------------------|-------------------|------------------|
| Engineering effort | Low | Medium | Very high | Very low |
| Code complexity post-launch | Same | Same | Permanent forever | Slight (μZ helper) |
| Block history preserved | ❌ | ❌ (1..H lost) | ✅ | ✅ |
| Balances preserved | Premine only | ✅ (modulo dust) | ✅ | ✅ |
| New genesis hash | ✅ | ✅ | ❌ | ❌ |
| Solves bridge math | ✅ | ✅ | ✅ | ❌ |
| Real-world precedent | XMR, ETH-Classic | Cosmos hub migration, Terra 2.0 | None at this scale | Iceland krónur |

## 8. Recommendation

Adopt **Option B** combined with the planned pre-launch RPC contract
bump from [`CANONICAL_UNITS_AUDIT.md`](./CANONICAL_UNITS_AUDIT.md) §3b.5.

Single coordinated release:
- New `FLOWERS_PER_ZION = 10⁶`.
- New RPC contract (`_flowers` everywhere, `_zion_display` for
  floats, drop `_atomic` and mis-named `_zion`).
- Snapshot-based re-genesis preserving every wallet's value.
- Migration receipt published for transparency.

If the repo owner is uncomfortable with re-genesis at all, fall back
to **Option D** as a stop-gap (display unit `μZION` in UI only,
no chain change), and revisit Option B after one year of mainnet
operation.

## Appendix A — Pseudo-code for snapshot exporter

```rust
// V3/L1/cli/src/snapshot.rs (proposed, not implemented)
pub fn export_snapshot(node: &NodeHandle, at_height: u64) -> Snapshot {
    let utxos = node.iter_utxos_at(at_height);
    let accounts = node.iter_accounts_at(at_height);
    let dao = node.dao_state_at(at_height);
    let bridge = node.bridge_locks_at(at_height);

    let mut snapshot = Snapshot::new(at_height);
    for (outpoint, output) in utxos {
        snapshot.add_utxo(outpoint, output);
    }
    for (addr, balance_flowers) in accounts {
        snapshot.add_account(addr, balance_flowers);
    }
    snapshot.dao = dao;
    snapshot.bridge_locks = bridge;
    snapshot
}
```

## Appendix B — Pseudo-code for genesis converter

```rust
// V3/L1/cli/src/genesis_builder.rs (proposed, not implemented)
pub fn build_genesis_from_snapshot(
    snapshot: &Snapshot,
    new_flowers_per_zion: u64, // = 1_000_000
) -> GenesisBlock {
    let divisor = OLD_FLOWERS_PER_ZION / new_flowers_per_zion; // = 1_000_000
    let mut dust_burn: u64 = 0;

    // 1. Premine outputs (14 slots) — addresses unchanged, amounts converted.
    let mut outputs = Vec::new();
    for original in PREMINE_OUTPUTS.iter() {
        let new_amount = original.amount_flowers / divisor;
        dust_burn += original.amount_flowers % divisor;
        outputs.push(PremineOutput {
            address: original.address.clone(),
            amount_flowers: new_amount,
            label: original.label.clone(),
        });
    }

    // 2. Snapshot-receiver output — single output that the H+1 tx will
    //    distribute to the accounts/utxos from the snapshot.
    let snapshot_total: u64 = snapshot.iter_amounts()
        .map(|a| a / divisor)
        .sum();
    let snapshot_dust: u64 = snapshot.iter_amounts()
        .map(|a| a % divisor)
        .sum();
    dust_burn += snapshot_dust;

    outputs.push(PremineOutput {
        address: SNAPSHOT_RECEIVER_ADDRESS.clone(),
        amount_flowers: snapshot_total,
        label: format!("snapshot-from-h{}", snapshot.height),
    });

    GenesisBlock::new(outputs, dust_burn)
}
```
