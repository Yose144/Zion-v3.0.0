# V3.1 Integration Plan — Native Wiring of the Four Moves

> **Goal:** Define the **exact, error-free native integration** of the four structural moves
> inside the clean `V31/` tree:
>
> 1. **Bridge ↔ WARP** — unify into a single L2 bridge family (shared types, shared adapter trait, shared memo/decimal/RPC layer).
> 2. **AuxPoW → Miner** — merge the standalone `AuXpow/` crate *into* `V31/L1/miner/` so there is **no `AuXpow` path dependency**.
> 3. **ZionDex → L2** — relocate the three independent ZionDex workspaces into `V31/L2/ziondex/` as first-class workspace members.
>
> This plan is the **engineering companion** to [`V3.1_MIGRATION_PLAN.md`](./V3.1_MIGRATION_PLAN.md).
> The migration plan says *what* moves and *where*; this plan says *how the seams weld together without errors*.
>
> **Status:** 🔵 Planning (pre-3.0.9)  
> **Update 2026-07-27:** Target L2 unification crate is **Multi-Chain** (`V31/L2/multichain`) per [`MAINNET_ALPHA_L2_UNIFICATION.md`](../3.0.8/MAINNET_ALPHA_L2_UNIFICATION.md). Integration details will be updated once the unified crate structure is finalized.  
> **Timing:** Executed during migration Phases 2–3 (post-3.0.9), on the `v3.1-migration` branch.  
> **Related:** [`V3.1_MIGRATION_PLAN.md`](./V3.1_MIGRATION_PLAN.md) §5, §7 (Phases 2–3), [`MAINNET_ALPHA_L2_UNIFICATION.md`](../3.0.8/MAINNET_ALPHA_L2_UNIFICATION.md)

## 0. Guiding principles (apply to all four integrations)

| # | Principle | Why |
|---|-----------|-----|
| P1 | **One source of truth per type.** No duplicate `ExternalCoin`, no duplicate `ChainId`, no duplicate decimal constants. | Duplicates drift; drift causes silent bugs at the L1/L2 boundary. |
| P2 | **Native = in-process Rust, not HTTP.** Where two crates now talk over localhost HTTP, the V31 versions share a trait or call directly. | HTTP is a deployment boundary, not an integration boundary. Native wiring means `use` paths, not `reqwest`. |
| P3 | **HTTP stays only where deployment isolation is real.** ZionDex Router ↔ WARP stays HTTP because the router is a separately deployable service. | Don't over-couple services that have different lifecycles. |
| P4 | **Feature flags gate optional backends, not optional integrations.** GPU backends are feature-flagged; the AuxPoW↔Miner seam is always-on. | The merge must not regress the always-on path. |
| P5 | **Tests move with the code.** Every crate's `tests/` directory migrates intact; integration tests are added at the seam. | A move that drops tests is not a clean move. |
| P6 | **No silent fallback.** If a shared type is used, both sides must compile against the *same* version. No `#[allow(dead_code)]` to silence mismatches. | Silent fallback hides the exact drift we're trying to eliminate. |

## 1. Integration A — Bridge ↔ WARP (unified L2 bridge family)

### 1.1 Current state (the problem)

| Aspect | Bridge (`V3/L2/bridge`) | WARP (`V3/L3/warp`) | Drift |
|--------|--------------------------|----------------------|-------|
| **L1 types dep** | `zion-l1-types` (path) | none — own `ZionL1Adapter` | WARP duplicates L1 RPC + address logic |
| **Memo format** | `BRIDGE:<chain>:<addr>` | `WARP:1:<chain>:<addr>` | Two parsers, no shared prefix logic |
| **Decimal conversion** | `FLOWERS_PER_ZION=1e6`, height-aware | `convert_decimals(from,to)` generic | Two implementations of the same 6↔18 conversion |
| **Chain abstraction** | none (hardcoded L1 + EVM watchers) | `ChainAdapter` async trait (12 families) | Bridge can't reuse WARP's adapter plumbing |
| **Status enum** | `BridgeStatus` (6 states) | `WarpStatus` (9 states) | Semantically overlapping, not unified |
| **Validator set** | 5/5 multisig (EVM contracts) | configurable quorum (default 3/5) | Two key-loading paths |
| **DB** | `BridgeDb` (SQLite: `l1_locks`, `evm_burns`) | `TransferDb` (SQLite: `transfers`) | Two schemas, two backup paths |
| **REST API** | Prometheus metrics only (port 9100) | Full REST (port 9333/8453) | Two servers, no shared middleware |
| **Code coupling** | ZERO (no `warp` imports) | ZERO (no `bridge` imports) | Only docs cross-reference |

**Root cause:** Bridge was built first (EVM-only, 3.0.4); WARP was built later (universal, 3.0.6) as a superset but never folded Bridge's EVM path back in. They now duplicate the entire L1↔EVM transfer pipeline.

### 1.3 Concrete welding steps

#### Step A1 — Create `V31/L2/types` (the shared seam)

New crate `zion-l2-types`. It depends on `zion-l1-types` and re-exports the chain primitives.

**What moves here:**
- `ChainAdapter` trait (from `V3/L3/warp/src/adapter/mod.rs`) — becomes the single adapter abstraction for both Bridge and WARP.
- `ChainId`, `ChainFamily` (from WARP's `types.rs`) — re-exported; L1/types keeps the canonical `L1Block` and address helpers.
- Unified `TransferStatus` enum — superset of `BridgeStatus` + `WarpStatus`:
  ```
  Pending, Detected, AwaitingFinality, Validating, QuorumReached,
  Executing, Completed, Failed, Timelocked
  ```
  (Bridge's 6 states map 1:1 into this; WARP's `TimelockHold` → `Timelocked`.)
- Unified memo parser — handles both `BRIDGE:` and `WARP:` prefixes, returns a `BridgeMemo { protocol, version, chain, address }` struct.
- Decimal conversion — single `convert_amount(value, from_decimals, to_decimals)` + height-aware L1 variant for legacy pre-3.0.3 blocks.

**What does NOT move here:** config structs, DB schemas, validator logic — those stay Bridge/WARP-specific.

#### Step A2 — Refactor Bridge to use `ChainAdapter`

- Bridge's `l1_watcher.rs` → becomes a `ZionL1Adapter` (implements `ChainAdapter`).
- Bridge's `evm_watcher.rs` → split into per-chain `EvmAdapter` impls (Base, Arbitrum, BSC, Polygon) that implement `ChainAdapter`.
- Bridge's `relayer.rs` → calls `adapter.execute_mint()` instead of hand-rolled EVM tx logic (the tx logic moves into `EvmAdapter`).
- Bridge's `types.rs` → deleted; uses `zion-l2-types`.
- Bridge's `config.rs` → `BridgeConfig` now holds `Vec<ChainConfig>` (same shape as WARP's `WarpConfig.chains`).

**Result:** Bridge is now a *specialized* multi-chain relay that uses the same adapter trait as WARP. It handles only EVM + L1; WARP handles EVM + L1 + 10 non-EVM families. They share the trait, not the implementations.

#### Step A3 — Refactor WARP to use `zion-l2-types`

- WARP's `adapter/mod.rs` → `ChainAdapter` trait removed (now in L2/types); WARP re-exports it.
- WARP's `adapter/zion_l1.rs` → deleted; uses Bridge's `ZionL1Adapter` (or a shared one in L2/types if both need it — see decision below).
- WARP's `types.rs` → `ChainId`, `ChainFamily`, `WarpStatus` removed; uses L2/types.
- WARP's `protocol.rs` memo parsing → delegates to L2/types `parse_memo()`.

**Decision: where does `ZionL1Adapter` live?**
- If Bridge and WARP both need it → it lives in `V31/L2/types/src/zion_l1_adapter.rs` (shared).
- If only Bridge needs it (WARP uses HTTP to L1) → it stays in Bridge.
- **Recommendation:** shared in L2/types, because both services watch L1 locks. One adapter, two consumers.

#### Step A4 — Unify validator key loading

- Both Bridge and WARP load validator keys from env vars / config.
- Create `V31/L2/types/src/validator.rs` with `ValidatorSet` (key loading, threshold check, signature aggregation).
- Bridge's `validator.rs` and WARP's `validator.rs` → both delegate to L2/types.
- Bridge keeps its 5/5 threshold; WARP keeps its configurable quorum — both are just `ValidatorSet` configs.

#### Step A5 — Keep REST APIs separate (P3)

- Bridge keeps its Prometheus-only endpoint (port 9100).
- WARP keeps its full REST API (port 8453).
- **Do NOT merge into one server.** They are separately deployable services with different operational concerns.
- Shared middleware (rate limiting, auth) → extracted to L2/types if duplicated, else left alone.

#### Step A6 — DB schemas stay separate

- `BridgeDb` and `TransferDb` remain separate SQLite databases.
- They track different things (Bridge: L1 locks + EVM burns; WARP: universal transfers).
- **Do NOT merge schemas.** Forcing one schema would break the universal-vs-EVM distinction.
- Shared: only the connection/backup pattern, which is trivial.

### 1.5 Risks (Integration A)

| Risk | Mitigation |
|------|------------|
| WARP's 499+ tests break on `ChainAdapter` move | Move trait first, run tests, fix imports incrementally. One PR per adapter family if needed. |
| Bridge's EVM watcher refactor breaks EVM tx signing | Keep `evm_tx.rs` intact; only the *calling* layer changes. Add a signing round-trip test. |
| `ZionL1Adapter` shared ownership dispute | Put it in L2/types; both Bridge and WARP are consumers. No one "owns" it. |
| Memo parser change breaks live L1 transactions | Parser is additive (handles both prefixes); old `BRIDGE:` format still parsed. No L1 fork needed. |
| Decimal conversion height-awareness lost | Keep the height-aware variant in L2/types; both Bridge and WARP call it for L1 amounts. |

```
├── src/types.rs              (DUPLICATE ExternalCoin, CoinProfile, JobPackage)
└── csrc/{cuda,metal,opencl}  (GPU kernels)
```

**Three drift problems:**
1. **Duplicate `ExternalCoin` enum** — `AuXpow/src/types.rs` defines the same 33-coin enum as `V3/L1/cosmic-harmony/src/profit_router.rs`. They must stay in sync manually.
2. **Two GPU backends** — AuXpow has `gpu_miner.rs` (OpenCL for external coins); Miner has `gpu_backend.rs` (OpenCL/CUDA/Metal for ZION + external). They share kernels via `csrc/` includes but have separate dispatch logic.
3. **Two profit routers** — `autonomous.rs` uses `zion_cosmic_harmony::profit_router`; AuXpow has `AuxPowScheduler` with its own profit logic + circuit breaker. The scheduler is never called from the miner.

**Uncommitted changes (in `V3/`, not yet committed):**
- `AuXpow/src/auxpow_client.rs` — clears per-job state on reconnect (fixes VRSC "Job not found" rejections).
- `V3/L1/miner/src/autonomous.rs` — adds `KRX` coin fallback revenue.
- `V3/L1/miner/src/main.rs` — pre-scans external share drain (reduces share submission lag from ~10s to ~0s).

These three fixes are **production hotfixes** that must be carried into V31 intact.

#### Step B4 — Unify GPU dispatch

Current: two GPU dispatch paths.
- `gpu_backend.rs` — ZION GPU mining (Deeksha, VerusHash) + external GPU dispatch (delegates to `zion_auxpow::gpu_miner`).
- `AuXpow/src/gpu_miner.rs` — OpenCL-only external coin GPU miner.

Target: **one `gpu_backend.rs`** that handles all GPU dispatch (ZION + external). The external-coin OpenCL kernels from `gpu_miner.rs` are folded into `gpu_backend.rs`'s `opencl_external` module (which already delegates to them). The delegation becomes a direct call.

**Action:**
- Move `gpu_miner.rs` logic into `gpu_backend.rs::opencl_external` (or keep as `auxpow::gpu_miner` submodule called directly — no trait boundary, just `use`).
- Remove the `zion-auxpow/gpu-opencl` feature flag from miner's Cargo.toml; GPU features are now `gpu-opencl`, `gpu-cuda`, `gpu-metal` on the miner crate directly.
- `csrc/` kernels are compiled by the miner's `build.rs`, not by a separate AuXpow build script.

#### Step B5 — Integrate `AuxPowScheduler` into `autonomous.rs`

Current: `autonomous.rs` uses `zion_cosmic_harmony::profit_router::fetch_live_profit_estimates()` and has its own `AutonomousProfitRouter`.

Target: `AutonomousProfitRouter::new()` instantiates `crate::auxpow::scheduler::AuxPowScheduler` with `SchedulerConfig`. The scheduler provides:
- Profit-switching with circuit breaker (already implemented in AuXpow).
- Live profit estimates (already implemented).
- Coin selection (already implemented).

`AutonomousProfitRouter` becomes a thin wrapper that translates scheduler output into the miner's stream-config format.

**Action:**
- `autonomous.rs`: replace `fetch_live_profit_estimates()` call with `scheduler.next_best_coin()`.
- Keep `fallback_revenue_usd_per_day()` as the scheduler's fallback (already there).
- The uncommitted `KRX` fallback addition carries over.

#### Step C8 — Native ZionDex ↔ WARP integration (optional, P3)

Current: ZionDex Router calls WARP via `POST http://127.0.0.1:8453/transfers/outbound`.

- ZionDex `router/src/types.rs::ChainId` → re-export from `zion-l2-types`.
- ZionDex `executor.rs` decimal conversion → use `zion-l2-types::convert_amount()`.
- This is a refactor, not a migration blocker.

## 4. Execution order (dependency graph)

The four integrations have a dependency order:

```
Integration B (AuxPoW → Miner)     ← independent of A and C
Integration A (Bridge ↔ WARP)      ← independent of B and C
Integration C (ZionDex → L2)       ← independent of A and B
                                      (but C's optional type unification depends on A's L2/types)
```

**All three are independent and can run in parallel** on the migration branch (different directories, no file conflicts).

**Recommended order (sequential, for safety):**

1. **C first (ZionDex → L2)** — lowest risk, purely mechanical, builds confidence.
2. **B second (AuxPoW → Miner)** — medium risk, large file move, but self-contained in L1.
3. **A third (Bridge ↔ WARP)** — highest complexity (new L2/types crate, trait extraction), benefits from having L1 and L2 stable first.

**Parallel option:** If three engineers are available, A/B/C can run in parallel on separate sub-branches of `v3.1-migration`, merged sequentially.
