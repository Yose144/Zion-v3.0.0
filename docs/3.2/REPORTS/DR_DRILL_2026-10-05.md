# DR Test — Single-Node Restore from the Latest Edge Backup

**Date:** 2026-10-05 · **Status:** PARTIAL (limited restore test; **not** a full or off-site DR drill) · **Author:** Devin (autonomous)

> **Correction (2026-10-05, internal audit):** the first version of this report called the test a "full off-site DR drill — PASSED". That was wrong. The sections below describe what was actually done and what is still missing. See `INTERNAL_AUDIT_2026-10-05.md` §3 and IA-08.

---

## 1. What was actually tested

1. Downloaded the latest automated Edge backup archive to the operator machine.
2. Extracted it and ran SQLite integrity checks on selected databases.
3. Started **one** `zion-node` from the restored `node.db`, isolated (no peers), on the operator machine.
4. Measured the time from download start until the node answered RPC.

## 2. Backup inventory (as observed)

| Item | Detail |
|---|---|
| Archive | `zion-edge-20261005_073410.tar.gz` (≈305 MB), produced by the host's backup timer (every 4 h; retention 14 daily + 4 weekly) |
| Contents | L1 node DBs (3×) + pool store, L2–L6 SQLite DBs, OASIS JSON, env/config files, systemd units, nginx config, TLS material, key files |
| Method | `sqlite3 .backup` for DBs, `cp` for config |
| Location | **only on the production host** (no off-site copy) |
| Encryption | **none** (env files with API keys, the validator key and the WARP operator key are in plaintext) |

## 3. Results

| Metric | Value |
|---|---|
| Download (305 MB) | 58 s |
| Extract | 8 s |
| `PRAGMA integrity_check` | `ok` for `node.db`, `dao.db`, `warp_multichain.db`, `free_world.db`. `issobella.db` was **not** checked. |
| Node start → RPC answering | ~10 s (tip-pinned UTXO cache) |
| End-to-end for this limited scenario | ≈ 81 s (download + extract + start) |
| Restored tip | height 69,791 (block time 02:13 UTC); archive created 07:34 UTC |
| Premine | the RPC **constant** reported 16.78 B. This was **not** verified against the restored UTXO set. |

## 4. What was not done

- No off-site copy exists, so off-site recovery could not be tested at all.
- Only the node was restored. Pool, multichain/WARP, DAO, ZIS, L3–L6 and the web app were not restored or started.
- The restored node did not sync with peers, so catching up to the live tip was not shown.
- The restored tip was not compared with production at the time of the test.
- No RPO was measured against a real failure: "≤ 4 h" is just the backup interval.
- Restoring key material and env (and rotating it) was not exercised.

## 5. Security findings from the test

- **IA-08 (High):** plaintext secrets inside the archive, and no off-site location.
- The extracted local copy (including env files and keys) was **deleted** from the operator machine on 2026-10-05.

## 6. Requirements for a real DR drill (Stable gate)

1. Encrypted archives, encrypted to a public key whose private half is kept offline, shipped to a second location.
2. Full-stack restore on a clean host: nodes (with peer sync to the live tip), pool, multichain, DAO, ZIS, L3–L6, web, nginx/TLS.
3. Verification:
   - tip and UTXO totals compared against production, premine checked from the UTXO set
   - integrity of all DBs, including `issobella.db`
   - service health
4. Measured RTO for the full stack and measured RPO for a simulated failure time.
5. Exercise key/env restore and the rotation procedure.
