feat(beam): pass 104-byte BeamHash III solution through miner→pool→upstream

The GPU solver for BEAM (BeamHash III) produces a 104-byte solution blob,
but the existing share-forwarding pipeline only carried 32-byte mix hashes
(Ethash/KawPow). The solution was silently dropped at multiple stages,
causing upstream beam.2miners.com to reject every share with "invalid
solution" / "wrong solution length".

Changes (end-to-end solution plumbing):
- V3/L1/miner/src/gpu_backend.rs: GpuBatchResult gains `solution: Option<Vec<u8>>`;
  GpuScanOutcome gains `solution_blob`; multi-GPU merge preserves the first
  solution found; all construction sites updated.
- V3/L1/miner/src/main.rs: ExternalShareResult gains `solution_blob`; both
  mining loops (synchronous + pipelined) propagate the blob from
  GpuBatchResult → GpuScanOutcome → ExternalShareResult; submit_external_share
  and the ZION submit path encode the blob as mix_hash_hex when present.
- V3/L1/pool/src/lib.rs: new `solution_message_with_solution_blob()` helper
  for the ZION stratum path (miner→pool).
- V3/L1/pool/src/bin/server.rs: ShareForwardRequest gains `solution` field;
  both mix_hash_hex parse sites now fall back to a variable-length solution
  blob when the hex is not a 32-byte mix hash; handle_external_share forwards
  the blob to the bridge; both try_forward call sites pass req.solution.
- AuXpow/src/share_forwarder.rs: try_forward accepts `solution: Option<&[u8]>`
  and encodes it as mix_hash_hex (which BEAM's submit_share already reads as
  the `output` field for BeamStratum). All call sites + tests updated.
- AuXpow/examples/e2e_pool_test.rs: updated for the new try_forward signature.

Verified: `cargo build --release -p zion-pool -p zion-miner -p zion-auxpow`
passes on Windows/MSVC.
